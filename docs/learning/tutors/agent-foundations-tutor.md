# Agent foundations — deep dive

*Companion to [`.github/agents/agent-foundations-tutor.agent.md`](../../../.github/agents/agent-foundations-tutor.agent.md). Read that first for the fast orientation; this document goes further. Self-check with `uv run agentic-pm-lab quiz agent-foundations-tutor`.*

This is the first course of the required Agent core module. It assumes Python
and nothing about agents or LangChain. Everything runs offline: the model is
scripted, so you can see every step without a network, an API key, or
sampling noise.

## What this actually is

An agent is a loop. Call the model with the conversation so far and the
tools it may use. If it asks for tool calls, run them and append each result
as a tool message. Call the model again. Stop when it answers without asking
for a tool, or when a limit you set is reached.

That is all a framework wraps. Anthropic's
[Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)
draws the line this course starts from: **workflows** are "systems where LLMs
and tools are orchestrated through predefined code paths", while **agents**
are "systems where LLMs dynamically direct their own processes and tool
usage". Both can use tools, retrieval, and memory. The difference is who
decides the next step.

The same article's advice shapes the course: "start with simple prompts,
optimize them with comprehensive evaluation, and add multi-step agentic
systems only when simpler solutions fall short", and "don't hesitate to
reduce abstraction layers and build with basic components". So you build the
loop by hand first (part 1), then run the identical loop in LangChain (part 2)
and see exactly what the framework does for you.

## Core concepts

- **The augmented LLM.** The building block: a model with tools, retrieval,
  and memory. An agent is this block in a loop.
- **Tool calling.** A tool is a name, a description the model reads, and a
  JSON Schema for its arguments. The model never runs code; it *asks* for a
  call, and your code decides whether and how to run it.
- **The observation.** A tool result goes back to the model as a message
  linked to the request by its call id. ReAct
  ([Yao et al.](https://arxiv.org/abs/2210.03629)) showed why interleaving
  reasoning with actions matters: grounding each step in what an action
  returned counters "hallucination and error propagation".
- **Stopping conditions.** The model decides when it is done, so the loop
  needs a limit it does not control. "Building effective agents" recommends
  "stopping conditions (such as a maximum number of iterations) to maintain
  control."
- **Tool design.** "Poka-yoke your tools": shape arguments so mistakes are
  hard to make. Keep the set small; Anthropic's
  [context-engineering article](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
  names "bloated tool sets that cover too much functionality" as a common
  failure mode.
- **Context engineering.** Context is a finite budget. "As the number of
  tokens in the context window increases, the model's ability to accurately
  recall information from that context decreases" (context rot). Aim for "the
  smallest possible set of high-signal tokens".
- **Structured output.** Asking for a format in the prompt is a request; a
  schema is enforcement. LangChain's
  [structured output](https://docs.langchain.com/oss/python/langchain/structured-output)
  uses the provider's native support when there is one, and tool calling when
  there is not.

## How this repository implements it

### Part 1: the loop by hand

`src/foundations/agent_loop.py` is one file of about 250 lines, much of it
explanation. `Tool` pairs a
hand-written JSON Schema with a function, and `Tool.spec()` is all the model
ever sees. `ScriptedModel` stands in for an LLM: it replays planned turns and
records what it was shown, so tests can check the model's view.

`run_agent()` is the loop. It shows the model only the tools in
`allowed_tools`, calls it, and on a turn with no tool calls returns
`stop_reason="answered"`. Otherwise it appends the assistant's tool calls to
the transcript, runs each through `governed_call()`, and appends a `tool`
message carrying the matching `tool_call_id`. After `max_steps` model calls
it stops with `stop_reason="max_steps"` and no answer.

Arguments arrive as text. `_parse_and_validate()` parses the JSON and checks
it against the schema. A malformed call does not crash the run: the error
goes back to the model as the tool message, so it can correct itself.

### Part 2: the same loop in LangChain

`src/foundations/langchain_loop.py` runs the identical loop. What moves into
the framework:

| Job | By hand | LangChain |
|---|---|---|
| Tool schema | Written as JSON Schema | Generated by `@tool` from type hints; the docstring becomes the description |
| Messages | Dicts with roles | `HumanMessage`, `AIMessage` with `tool_calls`, `ToolMessage` |
| Argument checks | `jsonschema.validate` | The generated schema, checked on `invoke` |
| Structured answer | Parse text yourself | `with_structured_output(YieldAnswer)` |
| Instrumentation hook | Spans you write | Callback handlers (`CallCounter`), plus the same spans |

What does **not** move: authorization, spans, and audit. `run_langchain_agent()`
sends every call through the same `governed_call()`. A framework makes a tool
easy to call; deciding whether it may be called stays in your code.

One detail was checked rather than assumed: LangChain's `GenericFakeChatModel`
implements neither `bind_tools` nor `with_structured_output`. The lab's
`ScriptedToolModel` subclasses it with a `bind_tools` that returns itself, and
`test_the_stock_fake_model_cannot_bind_tools` pins why.

## The four threads

Observability, traceability, governance, and evaluation are not later
courses bolted onto a working agent. They are in the loop from its first
line, and each has its own course later in Agent core.

| Thread | In the loop | Evidence |
|---|---|---|
| **Observability** | One `invoke_agent` span per run, a `chat` span per model call, and an `execute_tool {name}` span per tool call, named by the [OpenTelemetry GenAI conventions](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-spans.md) (status: Development). The real `interpolate_curve` tool's own span nests under the tool span. | `test_spans_follow_the_genai_conventions_and_nest_under_the_run` |
| **Traceability** | Audit records are written inside the run's span, and `record_audit_event` stamps the active trace id, so one id links the run, its spans, and every decision. This is the [W3C Trace Context](https://www.w3.org/TR/trace-context/) idea: the trace-id identifies "the whole trace". | `test_every_audit_record_carries_the_runs_trace_id`, and `test_a_fresh_process_run_shares_one_trace_id_with_its_audit` for a run in a new process |
| **Governance** | Least privilege twice: the model is shown only allowed tools, and `governed_call()` checks the allowlist again on every call. That second check is OWASP's [complete mediation](https://genai.owasp.org/llmrisk/llm062025-excessive-agency/) against Excessive Agency: a hidden tool can still be requested, by a hallucination or an injected instruction. | `test_a_forbidden_tool_is_refused_in_code_even_when_requested` |
| **Evaluation** | `src/foundations/grading.py` grades the outcome by default, as Anthropic's [agent evals guide](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) advises ("grade what the agent produced, not the path it took"), and checks the path only where it is a requirement: a forbidden tool never executed, a call budget, every record traceable. Grades are reported separately, never averaged. | `test_two_different_valid_paths_both_pass_the_outcome_grader` |

## Common pitfalls

- **Governance in the prompt.** "Never call place_order" in a system prompt
  lowers the chance of the request; it cannot prevent it. Only a check in
  code on every call can.
- **Crashing on a bad tool call.** A malformed call is something for the model
  to fix. Raising ends the run and throws away its work; returning the error
  as a tool message lets it recover.
- **No stopping condition.** A model that keeps choosing another tool call
  never ends on its own, and every turn costs money.
- **Grading the path.** Exact tool-sequence checks fail valid alternatives and
  reward conformity. Grade the outcome, and assert only the path properties
  that are requirements.
- **Letting the framework own authorization.** `bind_tools` decides what the
  model is offered, not what may run.
- **Reaching for an agent by default.** If every step is known in advance, a
  workflow is cheaper, faster, and easier to test.
